# Recommendations model plan

Status: proposed
Last updated: 2026-09-16
Feeds: issue #505 (unassigned activity pool and swipe triage)

## Outcome

A country-enrichable library of place recommendations that can be:

- gathered from a traveller's own saved pins (the immediate source),
- authored by hand in admin,
- generated by AI,
- searched by tag, city and activity type,
- swiped through on mobile and dropped onto a trip day.

This document is the data model and the sequencing. It does not implement anything.

---

## What the real source data actually looks like

The plan is grounded in the Taiwan map (`Taiwan Saved Posts - Chris`, 84 pins, exported as KML). Every pin carries the same six fields:

| Field | Example |
| --- | --- |
| `Location` | `Wang's Broth, Taipei, Taiwan` |
| `Category` | `Food & Drink` |
| `Area` | `Taipei` |
| `Notes` | `Michelin Bib Gourmand braised pork rice (Lu Rou Fan), 50+ years, budget-friendly (<$5)` |
| `Source` | `@doitforicecream` |
| `PostURL` | `https://www.instagram.com/doitforicecream/reel/DZzG8QAxblI/` |

Four measurements that drive the design:

1. **0 of 84 pins have coordinates.** The KML `<coordinates>` element is empty on every placemark. Geocoding is not an optimisation, it is a precondition for import.
2. **7 source categories, 13 app activity types.** `Sights & Landmarks`, `Food & Drink`, `Nature & Day Trips`, `Activities & Experiences`, `Night Market`, `Shopping & Souvenirs`, `Nightlife`. The mapping is lossy in both directions — `Night Market` is a *tag*, not a type — which is why the model needs a controlled type vocabulary **and** free-form tags.
3. **`Area` is not reliably a city.** 62 Taipei, 10 New Taipei City, then single pins for Kaohsiung, Tainan, Chiayi, Matsu, Yilan — plus `Taiwan` and `Taiwan-wide`. A recommendation must be attachable at country level with no city.
4. **Only 4 of 84 notes contain a price signal.** Cost band is sparse, derived, and must be nullable.

There are **56 distinct Instagram creators** across 84 pins. Attribution is a first-class field, not a nice-to-have.

## Draft data structure

### Core entity

```ts
type RecommendationStatus = 'draft' | 'in_review' | 'published' | 'rejected' | 'retired';
type RecommendationOrigin = 'import' | 'manual' | 'ai' | 'user_submission';
type CostBand = 'free' | '$' | '$$' | '$$$' | '$$$$';
type GeocodePrecision = 'rooftop' | 'exact' | 'approximate' | 'city' | 'country' | 'unknown';

interface Recommendation {
  id: string;                       // uuid, never a provider id
  slug: string;                     // stable, human-readable, unique per country

  // Place ---------------------------------------------------------------
  countryCode: string;              // ISO 3166-1 alpha-2, 'TW'
  regionCode: string | null;        // ISO 3166-2 when known
  cityName: string | null;          // null for country-wide entries
  citySlug: string | null;          // joins the existing destination city guides
  location: RecommendationLocation;

  // Content -------------------------------------------------------------
  locale: string;                   // language of title/summary/description
  title: string;
  summary: string;                  // one line; this is the swipe-card text
  description: string | null;       // markdown, long form
  activityTypes: ActivityType[];    // reuses shared/activityTypes.ts
  tags: string[];                   // normalized lowercase, searchable

  // Practical meta ------------------------------------------------------
  costBand: CostBand | null;
  costNote: string | null;          // 'NT$50-120 per bowl'
  currencyCode: string | null;      // ISO 4217
  openingHours: OpeningHours | null;
  typicalDurationMinutes: number | null;   // seeds the timeline item's duration
  bestTimeOfDay: Array<'morning' | 'afternoon' | 'evening' | 'night'> | null;
  seasonalMonths: number[] | null;  // 1-12, empty/null = year round
  bookingRequired: boolean | null;
  accessibilityNote: string | null;

  // Media ---------------------------------------------------------------
  image: RecommendationImage | null;

  // Provenance ----------------------------------------------------------
  origin: RecommendationOrigin;
  sources: RecommendationSource[];

  // Signals -------------------------------------------------------------
  likeCount: number;                // denormalized from recommendation_reactions
  saveCount: number;
  dismissCount: number;
  qualityScore: number | null;      // ranking input for the swipe deck

  // Lifecycle -----------------------------------------------------------
  status: RecommendationStatus;
  createdAt: string;
  updatedAt: string;
  publishedAt: string | null;
  reviewedBy: string | null;
}
```

### Supporting shapes

```ts
interface RecommendationLocation {
  lat: number | null;
  lng: number | null;
  address: string | null;           // as given by the source
  formattedAddress: string | null;  // as returned by the geocoder
  geocodePrecision: GeocodePrecision;
  googlePlaceId: string | null;     // provider id kept as a mapping, never canonical
  geocodedAt: string | null;
}

/**
 * Structured rather than free text, because the swipe deck and the planner both
 * need to answer "is this open on the day I am dropping it onto".
 */
interface OpeningHours {
  timezone: string;                 // IANA, 'Asia/Taipei'
  weekly: Array<{ day: 0 | 1 | 2 | 3 | 4 | 5 | 6; opens: string; closes: string }>;  // 'HH:MM', several ranges per day allowed
  closedDays: number[];             // explicit weekly closures
  exceptions: Array<{ date: string; closed: boolean; opens?: string; closes?: string }>;
  note: string | null;              // 'open 24h', 'seasonal, Apr-Oct'
  observedAt: string;               // opening hours go stale; this is when it was read
}

interface RecommendationImage {
  url: string;
  provider: 'google_places' | 'instagram' | 'generated' | 'upload' | 'stock';
  attribution: string | null;       // required for anything not generated or uploaded
  authorUrl: string | null;
  licenseNote: string | null;
  blurhash: string | null;          // the app already renders blurhash placeholders
  width: number | null;
  height: number | null;
}

interface RecommendationSource {
  kind: 'instagram' | 'google_maps' | 'web' | 'editorial' | 'ai' | 'user';
  handle: string | null;            // '@doitforicecream'
  url: string | null;
  capturedAt: string;
  note: string | null;
}
```

### Per-user reactions

The like counter on the row is a denormalization. The row that matters is per user, because the swipe deck must never show a dismissed card twice.

```ts
interface RecommendationReaction {
  recommendationId: string;
  userId: string;
  reaction: 'like' | 'save' | 'dismiss';
  tripId: string | null;            // set when the swipe happened inside a trip context
  createdAt: string;
}
```

Unique on `(recommendationId, userId)` so a swipe is idempotent and reversible — undo is a delete, not a second row.

## Storage

Mirror the conventions the destination layer already uses: queryable columns for anything filtered or sorted, JSONB for the rest, a private staging layer, and an audited import run.

| Table | Purpose | Public |
| --- | --- | --- |
| `recommendations` | The entity above | Published only |
| `recommendation_reactions` | Per-user like/save/dismiss | Own rows only |
| `recommendation_candidates` | Review queue for imported and AI-authored rows before publish | No |
| `recommendation_import_runs` | Run counts, failures, source, geocoder version | No |

Columns promoted out of JSONB, because the deck filters on them: `country_code`, `region_code`, `city_slug`, `status`, `origin`, `activity_types` (array), `tags` (array), `cost_band`, `lat`, `lng`, `like_count`, `quality_score`, `locale`.

Two notes that follow from how this repo works:

- Migrations in `supabase/migrations/*.sql` are **not applied by a deploy**. Whatever lands here has to be applied by hand per `docs/SUPABASE_RUNBOOK.md`, and said plainly as pending until it is.
- The destination tables (`destination_guides`, `destination_country_profiles`, `destination_content_overrides`) are read by `netlify/edge-functions/destinations.ts` straight over PostgREST with the anon key. Recommendations should be served the same way, which makes RLS the only thing standing between the anon key and the table. Published-only read, reactions restricted to the owning user.

### Relationship to the destination model

`docs/DESTINATION_MODEL_V2_PLAN.md` proposes a canonical `Place` model with a `poi` kind. Recommendations are **not** that model and should not wait for it:

- a `Place` is an identity — a thing that exists at a coordinate;
- a `Recommendation` is an opinion about a place — why go, what it costs, who said so.

Keep `citySlug` and a nullable `placeId` on the recommendation so the two can be joined later without a migration of meaning. Until the place model lands, `citySlug` plus coordinates is enough.

## Ingestion

### Importing a Google My Maps map

A public My Maps exports without authentication:

```
https://www.google.com/maps/d/kml?mid=<mid>&forcekml=1
```

The importer walks placemarks and maps `ExtendedData` to the model. The interesting part is what it cannot do directly:

1. **Geocode every pin.** No pin carries coordinates. Feed `Location` + `Area` + country to the geocoder, keep `googlePlaceId` and `formattedAddress`, and record `geocodePrecision`. Anything below `approximate`, or ambiguous between results, goes to `recommendation_candidates` rather than being guessed.
2. **Map `Category` to `activityTypes`,** and keep the raw category as a tag so nothing is lost:

   | Source category | `activityTypes` | Tags |
   | --- | --- | --- |
   | Food & Drink | `food` | `food-drink` |
   | Sights & Landmarks | `sightseeing`, `culture` | `landmark` |
   | Nature & Day Trips | `nature` | `day-trip` |
   | Activities & Experiences | `adventure` | `experience` |
   | Night Market | `food`, `shopping` | `night-market` |
   | Shopping & Souvenirs | `shopping` | `souvenirs` |
   | Nightlife | `nightlife` | `nightlife` |

3. **Split `Notes`.** It is doing three jobs at once — summary, cost signal, and trivia. Keep the raw text as `description`, and let the enrichment pass propose `summary`, `costBand` and `tags` as *candidate* values a human accepts.
4. **Record the creator.** `Source` and `PostURL` become a `RecommendationSource` with `kind: 'instagram'`. This is the attribution the images question below depends on.

Import is preview-then-apply, like the AtoBeach importer: a dry run that exits non-zero with totals and failures, and an `--apply` that writes.

### Two things a trial conversion of the real pins exposed

Converting a sample of the Taiwan pins into the shape above found both of these, and both are importer requirements rather than model changes:

**A single pin can cite several creators.** `Elephant Mountain (Xiangshan)` carries four handles in `Source` and four URLs in `PostURL`, semicolon-separated and in a different order from each other. `sources` is already an array, which holds up — but the importer has to split on `;`, pair handle to URL by matching the handle inside the URL path rather than by position, and drop a source it cannot pair rather than mis-attributing it.

**The category alone mis-types a pin.** The same pin is filed under `Sights & Landmarks`, which maps to `sightseeing, culture`, while its note reads *"Free 20-min hike, best sunset/skyline view of Taipei 101"* — that is `hiking` and `nature`, and `costBand: 'free'`. The category is a starting point; the note carries the truth. The enrichment pass must be allowed to *add* types and set a cost band from the note text, and because it is guessing, those stay candidate values a human accepts. A naive price regex over the same note also missed the word "Free" while catching "budget-friendly" elsewhere, which is the argument for enrichment by model rather than by pattern.

### The media question, which needs a decision before any image ships

Instagram and Google Places photos cannot simply be copied onto TravelFlow's CDN — both providers' terms restrict rehosting, and 56 of these creators own their footage. Three workable options, in order of preference:

1. **Reference, do not rehost.** Store the post URL and creator handle, render an attribution card that links out. Costs nothing, keeps the credit with the creator, gives a weaker visual.
2. **Generate.** An illustrative image per recommendation, clearly marked as generated. Consistent and safe; not the real place.
3. **Licensed stock or own uploads.** Best quality, highest effort.

The schema supports all three through `RecommendationImage.provider`; the decision is product and legal, not technical, and it should be made before the swipe deck is built, because a deck of cards without images is a different feature.

## AI

### Correction: there is no working AI activity generation today

`services/aiService.ts:1447`:

```ts
export const generateActivityProposals = async (_prompt, _location, _context) => {
  return [];
}
```

It is a deliberate stub — client-side provider calls were removed so the browser never holds a provider key, and the server endpoint that would replace it was never built. `AddActivityModal` calls it, renders an AI tab, and always lands on the empty state. **The "add an activity with AI" path in the current app does not produce anything.** I previously described it as working; it is not.

That makes the AI work here two things, not one:

1. **Build the missing endpoint** — a server route that proposes activities for a location, in the same shape `AddActivityModal` already expects. This fixes an existing broken path independently of recommendations.
2. **Author recommendations with AI** — same provider runtime, different output schema: full `Recommendation` rows for a country or city, written to `recommendation_candidates` with `origin: 'ai'` and `status: 'in_review'`.

Both live behind `netlify/edge-functions/` beside the existing `ai-generate*` routes and must follow `docs/AI_AGENT_FEATURE_GUARDRAILS.md`: no raw exceptions in the response, no `VITE_`-prefixed credential server-side, a forgiving model-facing schema and a strict internal one, and a run budget under Netlify's 60s synchronous limit — which means generating 80 recommendations is a batched or queued job, not one request.

**AI output is never published directly.** It lands in review. A model inventing a restaurant that does not exist is the failure mode that would poison the library.

### Extending the trip planner

Once the library exists, trip generation can prefer real recommendations over invented activities: retrieve published rows for the trip's cities, pass them as candidate context, and let the planner select and schedule them. That is a prompt and retrieval change, not a new model — and it is the payoff that makes the library worth filling.

## Admin

A new admin section, following the existing table and settings conventions in `docs/DESIGN.md` and `docs/DESIGN_SYSTEM_COMPONENTS.md`:

- list with filters on country, city, status, origin, activity type and tag;
- a single-row editor for every field above;
- the review queue — accept, edit-then-accept, reject — for imported and AI rows;
- an import screen that takes a My Maps URL or KML upload, shows the dry run, then applies;
- bulk publish and bulk retire.

## Serving and the link to #505

```
GET /api/recommendations?country=tw&city=taipei&types=food,nightlife&tags=night-market&limit=30&cursor=…
GET /api/recommendations/<slug>
POST /api/recommendations/<id>/reactions   { reaction: 'like' | 'save' | 'dismiss', tripId? }
```

The deck for #505 is a query against this endpoint minus the caller's existing reactions, ordered by `qualityScore` then `likeCount`. A `save` is what puts a recommendation into that issue's unassigned pool; assigning it to a day converts it into a normal `ITimelineItem`, carrying `title`, `description`, `activityTypes`, coordinates and `typicalDurationMinutes` across.

The conversion is the seam worth getting right: a recommendation is a library row shared by everyone, a timeline item is a copy owned by one trip. Copy on assign; never point a trip at a library row that an editor can later retire.

## Open questions

1. **Media**: reference, generate, or license? Blocks the deck's visual design.
2. **Who can submit?** Editors only, or travellers too? `origin: 'user_submission'` is in the model but the moderation path is not designed.
3. **Are likes global or per trip?** The model supports both; the deck's ranking changes depending on the answer.
4. **Locale**: one row per language, or a translations table? The Taiwan set is English-only, but the app ships nine locales.
5. **Duplicate policy** when two imports, or an import and the AI, produce the same place. Match on `googlePlaceId` first, then name plus proximity — needs a threshold.
