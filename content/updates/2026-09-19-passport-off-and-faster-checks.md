## Changes
- [x] [Changed] 🛂 The passport and its stamps are put away for now. It never grew into the feature it was meant to be, so rather than leave a half-finished corner on your profile we are taking it off the page until it can be built properly. Nothing you collected has been deleted — it is kept exactly as it was and will be there when the passport returns.
- [x] [Improved] ⏱️ Finished fixes and features reach the live site noticeably sooner. The safety checks that run before anything ships were repeating the same work several times over; they now run it once, without dropping a single check.
- [x] [Fixed] 🎲 Changes no longer get held up by a check that failed for no real reason. A quirk in how the test run shut itself down could report a failure even when every single test had passed.
- [ ] [Internal] 🛂 Passport deactivation is a single constant, `PASSPORT_FEATURE_ENABLED` in `services/passportService.ts`, gating the stamps section in `ProfileMetaPanel` and the `ProfilePassportDialog` on both `ProfilePage` and `PublicProfilePage`. Nothing was deleted: components, service, stored sticker selections and the `stamps.*` locale keys in all 11 locales are intact, so re-enabling is that one constant. The two browser tests that clicked into the passport now assert its absence and name the flag, so flipping it back fails them as a reminder to restore the interaction coverage.
- [ ] [Internal] 🧹 Added a global `afterEach(cleanup)` in `test/setupTests.ts`. Testing Library was never auto-cleaning under this Vitest setup, so React trees stayed mounted after their file finished; leftover scheduled work then ran against a torn-down jsdom and threw `ReferenceError: window is not defined`, which Vitest counts as an unhandled error and exits 1 on. Run 35091017552 shows the shape: `388 passed / 2136 passed`, exit 1, originating in `SplitFlap.test.tsx`. Guarded on `typeof document` because the default environment here is `node`.
- [ ] [Internal] ⚡ Switched Vitest to `pool: 'threads'`. The default `forks` pool re-imports the whole module graph per test file. Locally this is a consistent win over all 418 files: 65.9s → 49.2s wall, `import` 162.9s → 120.7s. **On CI it is not**: the first threads run measured 201s and the next 277s against a 273s `forks` baseline, so runner variance swamps the effect and vitest's own duration barely moved (272.78s → 275.78s). Kept for local iteration speed, where the wait is actually felt; it is one isolated commit if that trade stops being worth the footgun below.
- [ ] [Internal] ⏱️ Final measured pipeline: **14m25s → 9m44s**. The whole saving is the removed duplicate suite (build gate 526s → 253s); `test:core` went 273s → 277s. Recorded plainly because the earlier claim that the thread pool sped up CI came from a single run and did not survive a second.
- [ ] [Internal] 🕐 The threads pool broke `tests/unit/defaultTripDates.test.ts` on CI. That file sets `process.env.TZ = 'Europe/Berlin'` at module scope so it can reproduce the local-midnight-serializes-as-previous-UTC-day bug, and asserts the zone took effect; under `forks` the file owned its process, under `threads` the process timezone is already fixed. Node reads TZ once at startup, so neither `test.env` nor an in-worker assignment helps (both verified) — it is set on the vitest scripts in `package.json`. Europe/Berlin and not UTC deliberately: under UTC that scenario cannot be reproduced at all. Footgun to remember: per-file `process.env` mutation no longer isolates. Ordinary env vars are unaffected (Node gives each worker its own copy); only TZ is special.
- [ ] [Internal] 🔁 `pnpm build` begins with `pnpm test:core`, so PR Quality ran the full suite twice per run — once as its own step, then again inside the build gate. The gate now runs `pnpm build:netlify`, which differs from `build` by exactly that one leading script and is the command Netlify executes, so the gate also gained deploy fidelity. Measured saving: 275s of an 865s run.
- [ ] [Internal] ✂️ Split the PR-description checklist into its own `pr-checklist.yml`, which alone keeps the `edited` trigger; PR Quality now runs on `opened`/`synchronize`/`reopened` only. Three of the last seven PR Quality failures were that checklist step, and fixing a PR body used to re-run the entire pipeline. The guard script is copied over unchanged.
- [ ] [Internal] 🚦 Added `concurrency` groups with `cancel-in-progress` to both workflows. Run 35359972328 and two siblings show three complete runs on a single branch started within 22 seconds of each other.
- [ ] [Internal] 🚢 `netlify.toml` `[context.production]` also ran `pnpm build`, paying for a third full suite on billed Netlify minutes after PR Quality had already proved the same head commit green. Switched to `build:netlify`, matching the `[build]` default. Because `main` had no branch protection, this is paired with requiring the PR Quality and PR Checklist checks on `main`.
- [ ] [Internal] 🔬 Investigated parallelizing `scripts/prerender-routes.mjs` (165s of the run, ~40 routes, sequential). A 4-way page pool cut it 108s → 43s locally but was **reverted**: per-route `modulepreload` hints are collected between navigation and `data-tf-handoff-ready`, and under CPU contention far less of the boot waterfall has been requested by the time that flag flips. `faq.html` fell 64 hints → 31, `es.html` 67 → 35 — about half the boot graph losing the hint that exists to prevent an import waterfall. Prerendering is confirmed live in production (`data-tf-prerendered-root` with 60–67 hints on `/`, `/features`, `/de`, `/pricing`), so this would have been a real regression.
- [ ] [Internal] 🧭 Closing the hint window at `networkidle` instead made counts perfectly reproducible across parallel runs, but polluted them: `pricing.html` picked up `MarketingHomePage`, `FeaturesPage`, `InspirationsPage` and `UpdatesPage` chunks from the navigation prefetcher. The existing comment calling post-handoff traffic "post-interaction warmup" is correct. Parallelizing prerender needs hint collection that does not depend on wall-clock request timing; recorded so the next attempt does not rediscover it.
- [ ] [Internal] 📎 The two `::view-transition-group-children` Lightning CSS warnings are unrelated to the passport — they come from the shipped blog list/detail transition and are the nested-group rule that issue #109 identified as the fix for unstable card/image clipping. Lightning CSS does not recognise the pseudo-element yet and passes it through; silencing it means bumping `lightningcss`, not deleting the CSS.
